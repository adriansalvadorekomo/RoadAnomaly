# Spec-driven development

This repository uses spec-driven development (SDD) for non-trivial feature work:
write the intent and the plan first, then implement against it. The decision is
recorded in [ADR-0013](adr/0013-spec-driven-development.md).

SDD is the per-feature loop. [CRISP-DM](adr/0007-crisp-dm-methodology.md) remains
the project lifecycle, and [`docs/experiments/`](experiments/) remains the only
home for run evidence. A spec is a plan, not a result.

## Tooling

The workspace is generated by **Spec Kit 1.2.2** with the OpenCode integration:

| Path | Purpose |
|---|---|
| `.specify/` | templates, scripts and the integration manifests |
| `.opencode/commands/speckit.*.md` | the `/speckit.*` entry points |
| `specs/` | the feature specs, plans and tasks produced by the workflow |

`.specify/memory/constitution.md` is the project constitution. It is normative
and the highest rule source, ratified by
[ADR-0014](adr/0014-adopt-project-constitution.md). The precedence order is
**constitution > accepted ADRs > [`AGENTS.md`](../AGENTS.md) > specs**.
Domain contracts such as [`docs/metrics.md`](metrics.md),
[`docs/xai.md`](xai.md) and [`docs/dataset.md`](dataset.md) remain normative
within their scope. Do not treat a spec as evidence that a requirement is
`implemented`; the [requirements matrix](validation/requirements-matrix.md)
defines that bar.

Personal agent state under `.opencode/` and `.commandcode/` is ignored. Only the
generated `speckit.*` commands are tracked.

## Artifact layout

Feature directories are sequential and kebab-cased:

```text
specs/
└── 001-normal-road-manifest/
    ├── spec.md          # what and why; user stories and requirements
    ├── plan.md          # how; architecture and file-level approach
    ├── tasks.md         # ordered, checkable implementation tasks
    ├── research.md      # optional: decisions made while planning
    ├── data-model.md    # optional: schema or type changes
    ├── contracts/       # optional: external interfaces
    └── quickstart.md    # optional: how to exercise the result
```

`specs/README.md` explains how to start one. Do not create a feature directory
for a chore, a typo fix or a documentation-only change.

## The loop

1. **Specify** — `/speckit.specify` turns the feature intent into `spec.md`.
   Link the ADRs, metric/XAI contracts or issue that constrain it.
2. **Clarify** — `/speckit.clarify` when the spec has unresolved decisions.
   Do not invent an answer that belongs in an ADR.
3. **Plan** — `/speckit.plan` writes `plan.md` and checks it against the spec.
4. **Tasks** — `/speckit.tasks` breaks the plan into ordered, verifiable work.
5. **Implement** — `/speckit.implement` executes the tasks. Update `tasks.md`
   as work lands.
6. **Verify** — run `make lint type test`; add or update tests with the code.

The Spec Kit commands are agent commands, not shell targets. The repository's
shell gate stays `make lint type test`.

## What belongs where

| Artifact | Home |
|---|---|
| Project principles and hierarchy | [`.specify/memory/constitution.md`](../.specify/memory/constitution.md) (normative; amendments need an ADR) |
| Feature intent, plan and tasks | `specs/NNN-name/` |
| Irreversible design decision | `docs/adr/` (new numbered record) |
| Normative metric definitions | [`docs/metrics.md`](metrics.md) |
| Normative XAI methods and evidence | [`docs/xai.md`](xai.md) |
| Run evidence and published numbers | `docs/experiments/NNNN-*.md` (official); `docs/experiments/learning/` (learning only) |
| Notebook roles, concept checks and learning records | [`dl/notebooks/README.md`](../dl/notebooks/README.md), [spec 002](../specs/002-notebook-workflow/spec.md) |
| Requirement status and evidence bar | [`docs/validation/requirements-matrix.md`](validation/requirements-matrix.md) |
| Dataset facts and evaluation protocol | [`docs/dataset.md`](dataset.md), [ADR-0001](adr/0001-evaluation-only-benchmark.md) |

If a spec and an accepted ADR disagree, the ADR wins. If a task and the
requirements matrix disagree about status, the matrix wins.

## A sensible first spec

The critical path is the normal-road manifest and the shared metric contract.
A first feature could be **001-normal-road-manifest**: pin the normal-road
release, class map, hashes and scene-grouped split manifest, then load it through
`dl/data/`. It has no benchmark dependency, and every later model and experiment
needs it. Use `/speckit.specify` with that scope, then link ADR-0010 and
`docs/metrics.md` from the spec.

## Scope

SDD does not change the evaluation protocol, the model lineup, the registry
promotion rule or the XAI gate. It also does not replace the ADRs: a decision
that is expensive to reverse still becomes an ADR, not a paragraph in a spec.
